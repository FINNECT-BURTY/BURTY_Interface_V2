# 부하 시험

## 목적

"몇 RPS 를 버티나"가 아니다. 현재 설정값은 **합리적 기본값일 뿐 실측이 아니다.**
무엇이 먼저 무너지는지 찾아 그 값을 조정하는 것이 목적이다.

| 값 | 현재 | 근거 |
|---|---|---|
| HikariCP 최대 커넥션 | 20 | **실측** — 조회 약 1,900 req/s 까지 대기 0, 그 지점에서 포화 (아래) |
| 스케줄러 풀 | 8 | 배치 5 + 큐 폴러 + 여유 |
| 비동기 풀 | 8~32 | 기본값 |
| 외부 API 타임아웃 | 연동별 5~15초 | 상대 SLA 추정 |

## 프로파일

| 프로파일 | 용도 | 조회 | 이체 | 소요 |
|---|---|---|---|---|
| `full` (기본) | 사용 패턴 재현 | 30 VU → 80 VU (생각시간 1~3초) | 5 TPS | 8분 |
| `saturation` | 포화 지점 탐색 | 초당 50 → 1000 반복 (생각시간 없음) | 끄고 돌린다 | 5분 |
| `smoke` | CI 회귀 감지 | 20 VU | 2 TPS | 70초 |

`full` 과 `saturation` 은 **다른 질문에 답한다.**

`full` 은 VU 수를 올린다. VU 는 요청 사이에 1~3초를 쉬므로, VU 를 아무리 올려도 초당
요청 수는 그 생각시간에 묶인다. "이 정도 동시 사용자에서 응답이 어떤가" 를 본다.

`saturation` 은 **초당 반복 수(도착률)** 를 직접 올리고 생각시간을 두지 않는다.
"초당 몇 건에서 무너지는가" 는 이쪽으로만 답할 수 있다. 반복 한 번이 조회 3건이므로
도착률 N 은 대략 3N req/s 다.

`smoke` 는 **용량을 재지 않는다.** CI 러너는 2 vCPU 에 DB·앱·부하 생성기가 한 머신에
같이 뜨므로, 나오는 숫자는 애플리케이션이 아니라 러너의 성능이다. 시나리오와 시딩이
엔드포인트·스키마 변경으로 깨졌는지, 그리고 커넥션 풀이 고갈되는지만 본다.
용량 산정은 스테이징에서 `full` 로 해야 한다.

## 실행

```bash
# 1. 표본 데이터 시딩 (빈 DB 를 상대로 한 측정은 아무 의미가 없다)
mariadb -u root -p burty < infra/loadtest/seed.sql

# 2. 레이트리밋을 끄고 애플리케이션 기동
BURTY_API_RATELIMIT_ENABLED=false SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun

# 3. 토큰 발급
TOKEN=$(curl -s -XPOST localhost:8080/api/v1/auth/token \
  -H 'Content-Type: application/json' -d '{"userId":"1"}' | jq -r .data.accessToken)

# 4. 시험 실행
k6 run -e BASE_URL=http://localhost:8080 -e TOKEN="$TOKEN" infra/loadtest/burty-load.js

# 4-b. 포화 지점 탐색 (이체는 끄고 돌린다 — 계좌 시딩과 LEVEL_3 증명이 필요하다)
k6 run -e BASE_URL=http://localhost:8080 -e TOKEN="$TOKEN" \
  -e PROFILE=saturation -e TRANSFERS=off infra/loadtest/burty-load.js
```

> `saturation` 은 임계값을 넘기는 것이 **목적**이다. k6 가 0 이 아닌 종료코드를 돌려주는
> 것은 실패가 아니라 무너지는 지점을 찾았다는 뜻이다. CI 에 넣지 말 것.

> **레이트리밋을 반드시 끌 것.** `/api/v1` 전반에 분당 300건 안전망이 걸려 있다.
> 켜둔 채로 돌리면 처리량이 아니라 레이트리밋 설정을 재게 된다.
> 레이트리밋 자체가 타당한 값인지는 별도로 검증할 문제다.

> **stub-mode 가 켜진 환경에서만 실행할 것.** 이체 시나리오는 실제 이체 경로를 탄다.
> 운영을 대상으로 돌리지 말 것.

이체 시나리오(`-e TRANSFERS=off` 로 끌 수 있다)는 계좌·연동기관 시딩과 `LEVEL_3`
단계 인증이 필요하다. `seed.sql` 은 조회 경로까지만 채우므로, 이체까지 측정하려면
해당 환경의 계좌 데이터를 별도로 준비해야 한다.

## CI

`.github/workflows/load-test.yml` 이 `smoke` 프로파일을 PR(`infra/loadtest/**` 변경 시)과
주 1회 스케줄로 돌린다. 실행 후 `hikaricp_connections_*` 지표를 로그에 남긴다.

## 시나리오

- **조회** — 30 VU 유지 후 80 VU 로 상승. 대부분의 트래픽이 조회이므로 여기서 먼저 무너진다.
- **이체** — 초당 5건 고정. 빈도는 낮지만 가장 비싼 경로다(은행 호출 + 트랜잭션 + 아웃박스).

멱등키는 매 요청마다 새로 만든다. 같은 키를 재사용하면 두 번째부터 재요청으로 처리되어
실제 이체 경로를 타지 않는다.

## 함께 볼 지표

k6 결과만 보면 원인을 알 수 없다. Grafana 에서 아래를 동시에 본다.

| 지표 | 무엇을 뜻하나 |
|---|---|
| `hikaricp_connections_pending` | 0 이 아니면 **커넥션 풀이 병목**이다 |
| `hikaricp_connections_active` | 20 에 붙어 있으면 포화 |
| `resilience4j_circuitbreaker_state` | 외부 연동이 차단됐는지 |
| `burty_outbox_dead_total` | 아웃박스가 적체·격리되는지 |
| `jvm_memory_used_bytes` | 힙 압박 |

## 결과를 어디에 반영하나

- 커넥션 대기가 발생하면 → `DB_POOL_MAX` 상향, **또는** 커넥션을 오래 잡는 코드를 찾는다.
  이체 경로는 의도적으로 외부 호출을 트랜잭션 밖에서 한다. 새로 추가된 코드가 이를
  어겼는지 `leak-detection-threshold` 경고로 확인한다.
- 이체 p95 가 튀면 → 은행 API 타임아웃과 서킷브레이커 임계값을 재조정한다.
- 조회 p95 가 튀면 → 캐시 적중률과 N+1 을 확인한다.

측정한 값은 이 문서의 표에 근거와 함께 갱신한다. **"기본값"이 아니라 "실측 후 이 값"이
되어야 한다.**

### 측정 결과 (2026-09-14)

**측정 환경.** Apple Silicon 노트북 한 대에 애플리케이션·MariaDB·k6 를 함께 띄웠다.
거래 5만 건, Redis 미사용, 레이트리밋 끔, 이체 시나리오 제외(조회 경로만).

#### `full` — 사용 패턴 재현

80 VU 까지, 8분 02초, 10,806 반복.

| | 값 |
|---|---|
| 조회 p95 (k6, 클라이언트 측) | 12 ms |
| HTTP 실패율 | 0 % |
| 최대 사용 커넥션 | 4 / 20 |
| 최대 커넥션 대기 | 0 |

**이 프로파일로는 무엇이 먼저 무너지는지 알 수 없었다.** VU 80 을 다 써도 요청 사이의
생각시간(1~3초) 때문에 실제 부하가 약 67 req/s 에 머물렀고, 풀은 20 중 4 까지만 쓰였다.
`saturation` 프로파일을 추가한 이유다.

#### `saturation` — 포화 지점 탐색

도착률 50 → 1000 반복/s, 5분, 92,530 반복.

구간별 (5초 간격, 지연은 **서버 측 평균** `http_server_requests_seconds`):

| 처리량 | 서버 평균 지연 | 풀 활성 | 풀 대기 |
|---|---|---|---|
| 890 req/s | 2.2 ms | 2 | 0 |
| 1,330 req/s | 2.4 ms | 5 | 0 |
| 1,876 req/s | 3.6 ms | 6 | 0 |
| **1,933 req/s** | 5.7 ms | **20 / 20** | **86** |
| 2,330 req/s | 70 ms | 20 | 139 |
| 2,558 req/s | 87 ms | 19 | 179 |

전 구간 합산: 조회 p95 648 ms (k6, 클라이언트 측), HTTP 실패율 0 %, 커넥션 타임아웃 0.

**첫 번째로 무너지는 것은 커넥션 풀이다.** 약 1,900 req/s 에서 활성이 20/20 으로 붙고
대기가 쌓이기 시작하며, 그 지점을 넘으면 서버 평균 지연이 2 ms 에서 87 ms 로 약 40 배가
된다. 다만 **실패한 요청은 없었다** — 커넥션 타임아웃도 HTTP 오류도 0 이다. 포화의 결과는
거절이 아니라 줄서기였다.

#### 이 숫자의 한계

- **절대값을 운영에 그대로 옮길 수 없다.** 앱·DB·부하 생성기가 한 머신에 있어 네트워크
  왕복이 없고, DB 도 같은 디스크를 쓴다.
- **마지막 구간은 부하 생성기와 경합한다.** 목표 도착률 1000 반복/s(≈3,000 req/s)에
  도달하지 못하고 2,558 req/s 에서 멈췄다. VU 가 1,500 상한에 붙었고 k6 자신이 같은 CPU 를
  썼다. 2,300 req/s 이후의 지연에는 서버가 아닌 몫이 섞여 있다.
- **힙은 측정하지 못했다.** 샘플러의 지표 패턴이 맞지 않아 `jvm_memory_used_bytes` 가
  수집되지 않았다. 힙 압박 여부는 이 측정으로 말할 수 없다.
- **이체 경로는 재지 않았다.** 계좌 시딩과 `LEVEL_3` 증명이 필요해 `TRANSFERS=off` 로 돌렸다.
  가장 비싼 경로가 빠져 있다는 뜻이다.

#### 반영

- **풀 20 을 유지한다.** 이 하드웨어에서 조회 약 1,900 req/s 까지 대기 없이 버틴다.
  시니어 자산관리 서비스의 예상 트래픽은 그보다 훨씬 낮다. 근거가 "기본값"에서 "실측"으로
  바뀐 것이 이번 측정의 성과다.
- 목표 트래픽이 1,900 req/s 에 근접하면 `DB_POOL_MAX` 를 올리기 전에 **DB 쪽 한계를 먼저
  본다.** 풀을 늘려도 DB 가 같은 동시성을 감당하지 못하면 줄서는 위치만 옮긴다.
- 스케줄러 풀·비동기 풀·외부 API 타임아웃은 **여전히 미실측이다.** 조회 부하만으로는
  건드려지지 않는 값들이라, 배치와 외부 연동을 함께 거는 시나리오가 있어야 한다.
